# Node/pnpm fallback (no Node on host)

Some environments this repo is worked in (see `deploy/web/check-requirements.sh` and the Podman deployment docs) have no Node/pnpm installed on the host at all — only a container runtime. To build or run tests there, run the pnpm command inside a throwaway container instead of failing or trying to install Node system-wide:

```bash
scripts/time-cmd.sh podman-core-test -- podman run --rm -v "$(pwd)":/repo -w /repo docker.io/library/node:22-alpine sh -c '
  set -e
  t0=$(date +%s)
  corepack enable && corepack prepare pnpm@9.15.9 --activate &&
  pnpm install --frozen-lockfile
  t1=$(date +%s)
  echo "[timing] pnpm install: $((t1 - t0))s"
  pnpm --filter @linkml-editor/core test
  t2=$(date +%s)
  echo "[timing] pnpm test: $((t2 - t1))s"
'
```

`scripts/time-cmd.sh` logs the total wall-clock time of the whole `podman run` (container start + everything inside it) to `test-timing/containers.log` at the repo root; the `t0`/`t1`/`t2` lines inside the container's `sh -c` script (plain POSIX `date`, since `node:22-alpine`'s shell is busybox `ash`, not bash) split that total into install-vs-test so a slow run can be attributed to the right phase instead of guessed at. The `set -e` at the top of that inline script is required, not decorative: replacing the original single `&&`-chain with separate lines (to insert the timing echoes) otherwise makes the script's own exit status come from its last command (an `echo`, always 0) regardless of whether `pnpm install` or `pnpm test` actually failed — confirmed empirically in this repo (a real vitest worker-timeout failure, exit 1 from pnpm, was silently reported as `exit=0` in `containers.log` before `set -e` was added). Verify this kind of exit-code-preservation empirically whenever restructuring a chained shell command to add instrumentation — it's easy to get the propagation subtly wrong. Both `test-timing/` and `.pnpm-store/` are gitignored — see "Clean up afterward" below; `test-timing/` doesn't need the same cleanup since it's tiny logs/JSON, not `node_modules`-sized. See `specs/backlog/test-timing-instrumentation-and-reliability.md` for the full timing/reliability plan this is part of.

This reliably takes several minutes — a cold `pnpm install` alone is commonly 60-90s, before any build or test time on top. **Always pass an explicit long timeout on the tool call running this** (5-10+ minutes); a default ~120s tool timeout will silently move the command to the background partway through `pnpm install`, which is disruptive mid-task and easy to mistake for a hang. This is a tool-invocation setting, not something to fix by adding `timeout N` inside the shell command itself — an in-shell `timeout` only kills the process at N seconds, it does not raise the tool's own execution budget.

**Always pin a full, exact `pnpm` version (`X.Y.Z`), never a bare major (`pnpm@9`, `pnpm@10`) or `corepack enable` alone with no `prepare` step.** `corepack prepare pnpm@<major>` has to make a live registry call to resolve which concrete patch version satisfies that major; on any transient failure of that specific call (seen in this environment as `Internal Error: Error when performing the request to https://registry.npmjs.org/pnpm`, easy to miss since it scrolls by before the real error), corepack silently falls back to whichever pnpm build is bundled in the base image (`node:22-alpine`'s corepack currently bundles pnpm 12.3.4) instead of failing loudly. pnpm 12.x has a real, unrelated breaking change — it no longer reads the legacy `pnpm.overrides` field in `package.json` — so installing under it against this repo's `pnpm-lock.yaml` (`lockfileVersion: '9.0'`) fails with `Error: ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`. **The symptom is a lockfile-mismatch error that has nothing to do with the lockfile actually being stale** — don't "fix" it by regenerating the lockfile with `--no-frozen-lockfile`. The fix is pinning the exact version above: an exact `X.Y.Z` skips the version-range resolution step entirely (verified — no registry call, no warning, clean install), so there's nothing left for a transient network hiccup to silently override. If `9.15.9` is ever no longer installable, pick any current pnpm 9.x patch release (the major must match this repo's `lockfileVersion: '9.0'`) and pin it exactly the same way, not as a bare `9`.

**Clean up afterward, every time:** because this bind-mounts the live working tree (not an isolated volume), `pnpm install` writes a real `node_modules` (and sometimes a stray `.pnpm-store`, if pnpm can't use its usual global store location inside the ephemeral container) onto the host. Both are gitignored, but neither is automatically removed. Run `rm -rf node_modules packages/*/node_modules .pnpm-store` when done — otherwise `deploy/web/Dockerfile.web`'s `COPY . .` (or any Dockerfile doing the same) will copy this into the build context on the next `podman build`/`podman-compose build`, which over this kind of container's bind-mount I/O can look exactly like a hang (real incident: turned a few seconds of copying into multi-minute stalls). This is also why `.dockerignore` at the repo root excludes `node_modules` and `.pnpm-store` explicitly — both must stay covered if either changes.

**vitest intermittently fails with `[vitest-pool-runner]: Timeout waiting for worker to respond` (~60s duration) whenever `node_modules` sits on a slow bind-mounted filesystem — this is not limited to the container path above.** Confirmed empirically (2026-09-15): a plain **native** invocation (Node/pnpm installed on the host, no container involved) of `pnpm --filter @linkml-editor/core exec vitest run io/__tests__/round-trip.test.ts` failed with this exact error 3/3 times on this WSL2 host, because the repo checkout — and its `node_modules` — were still on the `/mnt/c` drvfs mount (never relocated per "Native (non-container) dev setup" below). Adding `--environment node` (justified below, since that file has no DOM/React rendering) made it pass reliably. The root cause is jsdom-environment cold-start I/O latency against `node_modules` on a slow mount, not anything specific to running inside a container — the "container" framing in the rest of this note is where it was first observed and measured, but the mechanism triggers identically for a native process if `node_modules` hasn't been relocated off the slow mount. This is a jsdom-environment cold-start exceeding vitest's internal worker-ready timeout on a slow bind-mounted filesystem — not a code bug, and not tied to any specific test file (it hits an effectively random file each run: seen on `gitSlice.test.ts`, `editor-panels.test.tsx`, and `tours.test.ts` across different runs with no code changes to any of them). For a pure-logic test file with no DOM/React rendering, run it with the CLI flag `--environment node` to sidestep it — this is more reliable than routing it through `vitest.config.ts`'s `environmentMatchGlobs`, which did not reliably apply per-file in this environment when tried. **"No DOM/React rendering" is not the same as "no browser globals" — check for both before forcing `--environment node`, or the flag itself breaks the file.** Confirmed incident (2026-09-14): `src/__tests__/uiSlice.test.ts` has no React rendering at all, but tests `localStorage`/`Storage.prototype` directly — running it with `--environment node` (jsdom's `Storage` global doesn't exist under plain Node) failed 7 tests with `ReferenceError: Storage is not defined`, a real failure that looks exactly like a code regression, not the worker-timeout flakiness the flag is meant to route around. Before adding `--environment node` to a command, confirm the target file(s) don't touch `localStorage`/`sessionStorage`/`window`/`document`/`Storage` or any other jsdom-only global — if unsure, run without the flag first (the project's default jsdom environment handles both cases correctly) and only add it once the file is confirmed browser-global-free. **Correction, measured (2026-09-09):** this is NOT "a handful among hundreds of passing files" as this note previously claimed — 5 measured full-suite runs of `packages/core` with `node_modules` on the bind-mounted filesystem hit this error on **5 of 5 runs** (9-10 errors each, three specific files — `useTheme.test.ts`, `manifest.test.ts`, `editor-panels.test.tsx` — failing in every single run). See `specs/backlog/test-timing-instrumentation-and-reliability.md` ("Del 2 — Resultat") for the data and for a confirmed fix: relocating `node_modules` off the bind-mounted filesystem (onto a native disk, whether via a container bind-mount or a native install — see "Native (non-container) dev setup" below) eliminates this error entirely and cuts test runtime by an order of magnitude, because the underlying cause is I/O latency reading `node_modules` during jsdom setup, not something inherent to vitest's forked-worker pool.

## Native (non-container) dev setup, and its own reliability quirk

`scripts/setup-native-dev.sh` installs Node/pnpm natively on the host (via nvm/corepack, no `sudo`) instead of using the container path above, and attempts to relocate `node_modules` to native disk the same way (see previous note) while leaving the repo checkout itself on the slow mount. `scripts/check-native-dev-requirements.sh` is a read-only preflight check for it (same style as `deploy/web/check-requirements.sh`).

**The native Node/pnpm install itself is reliable and a clear win**: ~11-14s for `pnpm install --frozen-lockfile` versus ~226-228s via the container path (no container startup, no corepack re-prep each time) — measured on this WSL2 host.

**The `node_modules` relocation is NOT reliable, for reasons not yet understood.** On WSL2's drvfs (`/mnt/c`, mount option `symlinkroot=/mnt/`), an *absolute* symlink from the repo's mount to a native-disk target is silently broken for all reads/writes; a *relative* symlink target works for basic read/write. But a full `pnpm install` through such a symlink succeeded exactly once and then failed 7 of the next 8 attempts with `ENOTDIR`/`ENOENT` on pnpm's very first `fs.mkdir(node_modules, {recursive:true})` call — despite ruling out several hypotheses (fresh vs. cached packages, symlink count, warm-up timing, brand-new never-touched target paths). Confusingly, an *isolated* reproduction of the exact same "mkdir on a symlink pointing to an already-existing cross-filesystem directory" pattern succeeded reliably (5/5), even during the same stretch when real `pnpm install` runs were failing consistently — meaning something specific to pnpm's actual install process, not the symlink mechanism in general, is the real trigger. A failed install through one of these symlinks has also been observed to empty out the native target directory it pointed to, as a side effect of pnpm's error handling — don't assume a stale native directory from a prior failed attempt is safe to reuse as-is.

Given this, `scripts/setup-native-dev.sh` retries the relocation up to 3 times with real verification (checks actual files landed under the native path and that `node_modules/.bin` exists — not just pnpm's exit code, since that alone doesn't distinguish a real success from the empty-directory failure mode above), and falls back cleanly to a plain, non-relocated install with a clear warning if relocation can't be confirmed. It never leaves the repo half-broken. See `specs/backlog/test-timing-instrumentation-and-reliability.md` ("Del 2b") for the full investigation and what was ruled out, before attempting to debug this further.
